# План реализации: AI-улучшение изображений в book-editor

**Дата:** 2026-06-23 · **Статус:** план (код не пишем) · См. [задача.md](задача.md)

Учтены требования: (1) **pipeline**, (2) у клиента **часто много** low-DPI фото, улучшение
запускают **часто и в разных проектах одновременно**, (3) **лимиты file-platform**, (4) CRM
бесперебойна, (5) компьют на codex (ncnn), (6) хранить как **вариант** в file-platform.

---

## 1. Архитектура (3 сервиса)

```
[FE book-editor: «Улучшить» / «Улучшить все low-DPI проекта»]
        │ (gate: только low-DPI; dedup; квоты)
        ▼
[book-editor BACKEND]  ──create──►  EnhanceJob (Postgres)  ◄── очередь + история + квоты
        ▲                                   │
        │ progress/poll                     │
        │                          [enhance-worker (pm2 на crm)]  ← fair-share, global concurrency
        │                                   │  по стадиям (pipeline):
        │                                   ├─1 FETCH  ← file-platform GET content?variant=original  (без throttle)
        │                                   ├─2 ENHANCE→ codex enhance-service (ncnn, start/poll/result)
        │                                   ├─3 STORE  → file-platform POST internal variant-intake (enhanced)
        │                                   └─4 FINALIZE→ book-editor: photo.variants.enhanced=url, job=done
        ▼
[FE: before/after через ?variant=enhanced]
```

- **crm-бокс:** book-editor backend (API+БД) + лёгкий **enhance-worker** (как уже существующие
  `editor-assets-replication`/`cleanup` процессы). CPU-нагрузки почти нет — только I/O.
- **codex-бокс:** `enhance-service` (ncnn, тяжёлый CPU) — единственное место реального компьюта.
- **file-platform:** хранит и отдаёт вариант `enhanced`.

Разделение по веткам (правило воркспейса — раздельный review/merge):
- **A. enhance-service** (новый сервис на codex; git-workflow пока не обязателен, как payment/auth).
- **B. file-platform** (ветка через `create-agent-worktree.sh` + аудит; строгие инварианты).
- **C. book-editor** (ветка через `create-agent-worktree.sh` + аудит): BE + worker + FE.

## 2. Pipeline (per-image job) и почему так

Каждое улучшение = **EnhanceJob** со стадиями `queued → fetching → enhancing → storing → done|error`.
Стадии исполняет **enhance-worker** (отдельный pm2-процесс), не HTTP-запрос — чтобы:
- пережить рестарты (в отличие от in-memory у Макса — джобы в Postgres);
- держать **глобальный лимит конкурентности** к codex (узкое место);
- честно делить codex между проектами (fair-share, см. §3).

Стадии:
1. **FETCH** — скачать оригинал: `GET {FILE_PLATFORM}/api/upload-links/{token}/images/{imageId}/content?variant=original`
   (публично по токену, **этот эндпоинт без throttle** → массовая выкачка безопасна).
2. **ENHANCE** — отправить байты на codex `enhance-service` (async: `start`→`poll`→`result`,
   форма Макса). **Target-aware масштаб** (x2/x4 под размер ячейки, не всегда x4 — из Этапа 0).
   Лица (GFPGAN/CodeFormer) — **opt-in флагом** джобы.
3. **STORE** — залить результат в file-platform как вариант `enhanced` через **новый internal-эндпоинт**
   (x-internal-api-key, без throttle). Выход **≤20 МБ** (лимит файла) → кап разрешения + JPEG q.
4. **FINALIZE** — записать `photo.variants.enhanced = .../content?variant=enhanced`, job=done,
   тайминги/размеры в EnhanceJob (метрики).

Почему codex может pull/push сам — отложено (расширяет креды file-platform на codex); для MVP
байты гоняет worker на crm (I/O-light), codex остаётся «тупым» stateless-энхансером.

## 3. Массовость, конкурентность, fair-share (главное требование)

Сценарий: проект с сотней low-DPI фото × несколько проектов одновременно. Защита — **fair-share
поверх одного медленного codex**:

- **Глобальная конкурентность к codex = 1** (после бенчмарка возможно 2). Это и есть реальный throttle.
- **Fair-share по проектам:** worker берёт следующий job не FIFO, а **round-robin по проектам**
  (`lastServedAt` на проект → берём queued-job проекта с самым старым lastServed). Так 100 фото
  проекта A не блокируют 5 фото проекта B — они чередуются.
- **Bulk-enqueue:** «Улучшить все low-DPI проекта» создаёт N джобов разом (только low-DPI, dedup),
  показывает прогресс X/N. Per-project cap на размер очереди (напр. ≤200) → сверх — сообщение.
- **Квоты (defense in depth, L0–L3 из [задача.md](задача.md)):** per-user/день, per-project в очереди,
  глобальный дневной cap; на codex hard-backstop (один воркер + bounded queue + input cap + timeout).
- **Идемпотентность/dedup:** не ставить джоб, если у фото уже есть `enhanced` нужного масштаба или
  есть активный джоб (ключ `imageId+scale`).

**Лимиты file-platform — соблюдаются «бесплатно»**, потому что компьют медленный:
- запись `enhanced` ≈ 1 файл / 20–40 с ⇒ ~1.5–3/мин ≪ 120/60с (и internal-эндпоинт вне throttle);
- чтение оригиналов — через **unthrottled** content-эндпоинт;
- размер выхода капим **≤20 МБ**; держим вход ≤ ~24 Мпикс (и <40 Мпикс — лимит превью file-platform).
- Конкурентный доступ к самому codex ограничен нами (=1), так что параллельные проекты выстраиваются
  в честную очередь, а не штурмуют ни codex, ни file-platform.

## 4. Данные

**book-editor (Postgres, новая модель EnhanceJob = очередь + история + квоты):**
поля: `id, projectExternalId, userId, filePlatformImageId, uploadLinkToken, status, stage,
targetW, targetH, scale, faceRestore(bool), priority, attempts, queuedAt, startedAt, finishedAt,
waitMs, procMs, inBytes, outBytes, inW,inH,outW,outH, error`. Индексы для fair-share (`projectExternalId`,
`status`, `queuedAt`) и квот (`userId, finishedAt`). Метаданные фото (`variants.enhanced`) — в
существующем `photosMeta`/`PlacedImage` (как сейчас хранятся варианты).
*Prisma-миграцию коммитить `git add -f` (в crm миграции gitignored — грабля; в book-editor проверить).*

**file-platform (минимальное расширение, без AI в платформе):**
- `UploadImageVariantCode += enhanced` (enum) + в `allowedVariants` контента.
- Новый **internal**-эндпоинт приёма внешнего артефакта: `POST /internal/.../images/:imageId/variants/enhanced`
  (x-internal-api-key) — принимает байты, кладёт в storage по детерминированному ключу, создаёт
  `UploadImageVariant(enhanced)` + `UploadImageVariantArtifact` со статусом `ready`. **Компьют снаружи** —
  платформа только хранит (инвариант «не тащить AI/GPU в платформу» соблюдён).
- Отдача — существующий `?variant=enhanced`.
- *Альтернатива без правок file-platform:* лить enhanced как НОВЫЙ `UploadImage` (публичный upload) —
  проще, но это отдельное изображение, не «вариант» (теряем семантику). Рекомендую вариант-интейк.

**enhance-service (codex):** stateless, без БД (или in-memory как у Макса) — очередь/состояние держит
book-editor. На codex — только bounded single-worker как hard-backstop.

## 5. DPI-гейт (только low-DPI) — РИСК СНЯТ (разведка 2026-06-23)

book-editor **нативно работает в пикселях при 300 DPI** (`DPI=300`, `MM_TO_PX` в
`frontend/src/config/formats.ts`; форматы `PageFormat` с мм + `spreadWidthPx`). Портировать
`calculatePrintQuality` Макса (доли ячеек) **не нужно** — координаты слотов уже в 300-DPI px.

- **effectiveDpi уже считается в бэкенде:** `render.service.ts:8385` →
  `effectiveDpi = sourcePixels × 300 / placedPx`. Порог **`<200`** уже используется там же
  (`low_effective_dpi` warning, `render.service.ts:10043`) — это принятый в проекте порог.
- **Гейт:** `effectiveDpi = photoPixels × 300 / slotPixels < 200` → показать «Улучшить».
- **Target для ENHANCE** = пиксели слота (`clipWidth/clipHeight`, иначе `width/height`) — ровно
  столько px нужно под 300 DPI в этой ячейке.
- `PlacedImage` уже хранит `originalWidth/Height` (px фото) и `width/height`+`clip*` (слот в 300-DPI px).
- План: вынести расчёт из render.service в **общий util**, переиспользовать на BE (гейт+target) и FE
  (видимость кнопки). Нюанс: DPI зависит от размещения → для `PhotoPreviewModal` вне ячейки гейтить
  по самому крупному размещению фото в проекте (данные есть).

## 6. Этапы реализации (порядок)

1. **A. enhance-service на codex (MVP-движок):** обернуть ncnn Real-ESRGAN (Этап 0) в тонкий async-API
   (start/status/result), target-aware масштаб, single-worker + bounded queue + input cap + `/metrics`,
   pm2 (`max_memory_restart`, `nice`). Лица (GFPGAN/CodeFormer) — флаг, по умолч. off.
2. **B. file-platform:** код `enhanced` + internal variant-intake + отдача `?variant=enhanced` (ветка+аудит).
3. **C1. book-editor BE:** EnhanceJob, API (enqueue single/bulk, status, list), DPI-гейт, квоты, dedup.
4. **C2. book-editor enhance-worker:** pm2-процесс, fair-share scheduler, global concurrency, pipeline
   (fetch→enhance→store→finalize), ретраи, метрики.
5. **C3. book-editor FE:** кнопка в `PhotoPreviewModal.vue` + bulk «улучшить low-DPI проекта» + прогресс
   + before/after (`?variant=enhanced`) + сообщения о лимитах/квотах.
6. **Мониторинг:** `/metrics` codex, дашборд по EnhanceJob (очередь/тайминги/ошибки/по проектам),
   pm2 ресурсы codex + рестарты ai-assistant; алерты (очередь, error-rate, OOM-сосед).

Калибровка лимитов/конкурентности — после бенчмарка на реальном codex.

## 7. Масштабирование / железо

MVP мощнее железо НЕ требует. codex (класс рабочего бокса Макса) тянет low-volume; fair-share при
перегрузе **замедляется, не падает**, CRM не трогает. Слабый сервер ограничивает throughput
(~1 фото/20–40с → ~100–150/час), не корректность. Апгрейд — **только когда очередь реально копится**:
1. тюнинг (2 конкурентных джоба, если RAM позволит) → ~×2;
2. отдельный CPU-бокс под enhance (больше ядер + изоляция от ai-assistant);
3. **GPU-бокс** — ESRGAN ~1–2с вместо 20–40с (×10–20), и он нужен под генерацию фотокниг ⇒ один
   GPU-бокс закрывает и масштаб апскейла, и генерацию. Адаптер+очередь дают сменить компьют **без
   переписывания** book-editor/file-platform. Железо сейчас не покупаем — меряем спрос, апгрейдим по факту.

## 8. Решено (2026-06-23)

- **Хранилище консолидируем в file-platform**, от прочих облаков (Mail.ru) отказываемся ⇒ pipeline без
  спец-случаев. Следствие: существующие cloud/local-upload фото **мигрировать/загрузить в file-platform**;
  в book-editor сделать file-platform хранилищем по умолчанию (отдельный трек, частично вне этой задачи).
- **file-platform — на отдельном сервере** ⇒ storage и его воркер изолированы от CRM и codex (плюс).
  Метрики/лимиты этого сервера снять при реализации ветки B.

### Подтверждено руководителем (2026-06-23)
- **`enhanced` = настоящий вариант** в file-platform через новый **internal-эндпоинт приёма артефакта**
  (компьют снаружи) — выбран вариант A из §4. НЕ создавать отдельный UploadImage.
- **Границы сервисов = MVP (Вариант 1):** новый отдельный сервис ровно один — **enhance-service**
  («тупой» AI-движок ncnn на codex: картинка→улучшенная). Оркестрация (очередь EnhanceJob,
  worker/fair-share, квоты, DPI-гейт) — в **book-editor**; хранение варианта — в **file-platform**.
  Дорастить enhance-service до полноценного AI-сервиса (Вариант 2) — позже, под генерацию фотокниг.
- **Ветку A (enhance-service на codex) пока НЕ начинаем** — сначала разведка/уточнения.

## 10. Индекс веток / якоря при старте

Дату в slug проставляет `create-agent-worktree.sh` при создании (формат `<YYYY-MM-DD>-<slug>`).
Планировочный якорь — этот файл (`1/crm/tasks/…`, не под git). Постоянная история работ —
audit-доки **внутри каждого git-сервиса** (коммитятся).

| # | Сервис | git-workflow | Task-slug (вход) | Audit-док (история) | Содержимое |
|---|--------|--------------|------------------|---------------------|------------|
| A | **enhance-service** (codex, новый) | пока НЕТ (как payment/auth) | — | пока здесь, в `1/crm/tasks/…`; завести `docs/` когда появится репо | ncnn-движок + async-API + лимиты/метрики |
| B | **file-platform** | ДА — `bash ./scripts/create-agent-worktree.sh "enhanced-variant-intake"` | `docs/audits/<дата>-enhanced-variant-intake.md` | код `enhanced` + internal variant-intake + отдача |
| C | **book-editor** | ДА — `bash ./scripts/create-agent-worktree.sh "image-enhance"` | `docs/audits/<дата>-image-enhance.md` | EnhanceJob+API+квоты, worker/fair-share, DPI-util, FE |

Правила: каждая ветка — **раздельный review/merge**, нельзя смешивать сервисы в одном diff
(корневой CLAUDE.md). Перед стартом B/C — прочитать `WORKTREE-WORKFLOW.md` соответствующего сервиса.

**Порядок и зависимости:**
1. Зафиксировать **контракты** (API enhance-service: start/poll/result; intake file-platform) — на бумаге.
2. A, B можно вести **параллельно** (независимы).
3. C интегрирует оба → **последней**; в C сначала BE+worker, затем FE.
4. Калибровка лимитов/конкурентности — после бенчмарка на реальном codex (в рамках A).
