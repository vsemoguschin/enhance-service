# Воркеры зависали при обрыве сети

**Дата:** 2026-08-12 · **Ветка:** `agent/2026-08-12-hard-deadlines`

## Задача

Утром бокс потерял внешнюю сеть. После восстановления очередь стояла: `active=3`, `queue_len=13`,
`done` не рос, при этом процессов `codex exec` в системе не было. Помог только перезапуск сервиса.

## Аудит

**Таймауты складывались вместо того, чтобы ограничивать.** `_call` делал 3 попытки по
`urlopen(timeout=120)` плюс паузы — до ~360с на один запрос. `_run_task` проверял срок только
**между** итерациями цикла, поэтому фактическое время уходило далеко за `MAGNIFIC_TIMEOUT_S=150`:
POST + первый опрос статуса ≈ 12 минут. Скачивание результата шло с отдельным `timeout=180`.
Итого задача при мёртвой сети висела 10–15 минут вместо заявленных 150с, а с учётом fallback
(codex 150с, затем magnific) — дольше.

**Убивался только родительский процесс.** `subprocess.run(timeout=...)` при срабатывании таймаута
шлёт SIGKILL родителю; `codex` порождает дочерние процессы, которые продолжали держать открытым
pipe, и повторное ожидание вывода не завершалось. Отсюда картина «воркер занят, процессов нет».

Ошибки в логах инцидента: 6 задач упали с `network: <urlopen error timed out>` — это время сбоя.

## План

Один сквозной срок на задачу + снятие всей группы процессов агента.

## Результат

- `Deadline` в `magnific.py`: единый срок, `budget(cap)` отдаёт `min(остаток, потолок)`. Потолки:
  90с на отправку картинки, 30с на опрос статуса, 90с на скачивание результата. Повторы и паузы
  (включая ожидание после 429) обрезаются по остатку, при истёкшем сроке попытка не делается.
- `_run_task` проверяет срок и перед сном, и перед каждым вызовом.
- `codex_provider`: `Popen(start_new_session=True)` + `os.killpg(SIGKILL)` по таймауту, затем
  короткое дожатие pipe. Вывод читается из `communicate()`, а не из полей завершённого процесса.

**Проверки (на реальном коде):**
- бюджет вызова = min(остаток, потолок) — 10с при остатке 10с, 3с при потолке 3с;
- недоступный хост при сроке 6с → отказ за **6.0с** (прежнее поведение дало бы ~360с);
- истёкший срок → отказ без сетевой попытки;
- зависший агент с дочерним процессом снят ровно за таймаут, **процессов-сирот не осталось**
  (до фикса потомок пережил бы родителя и держал pipe).

**Худший случай теперь:** codex 150с + fallback magnific 150с ≈ 300с на задачу, что совпадает с
`ENHANCE_MAX_WAIT_MS=300000` у book-editor: клиент получит ошибку примерно тогда же, когда сервис
сдастся, — вместо бесконечного ожидания.

**Не проверено:** повторение самого инцидента (обрыв сети на боксе) — воспроизводить на проде не
стал.
