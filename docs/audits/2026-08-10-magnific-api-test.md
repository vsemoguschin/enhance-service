# Magnific API — проверка ключа и пригодности как внешнего провайдера

**Дата:** 2026-08-10 · **Ветка:** `agent/2026-08-10-magnific-api-test` · **Статус:** аудит + инструмент теста

## Задача

Появился ключ Magnific API (+ webhook signing secret). Проверить: годится ли внешний API как
движок апскейла вместо простаивающего локального Real-ESRGAN, сколько стоит и какого качества
результат. Тест — до любой интеграции в book-editor.

## Аудит

### Текущее состояние фичи

Улучшение фото реализовано целиком (C1 `enhance-service` / C2 `file-platform` / C3 `book-editor`),
задеплоено на codex и **выключено** флагом `ENHANCE_ENABLED=false`: на codex нет GPU, Real-ESRGAN x4
не укладывается и в 4.5 минуты на фото (llvmpipe, 2 ядра) — см. [../operations.md](../operations.md).
Развилка зафиксирована там же и в `#/#tasks/file-platform.md`: **GPU-бокс** (стратегия, ~1–3 с/фото,
сервис переносится как есть) либо **внешний API** («запустить прямо сейчас»).

### Что сейчас делают в веб-версии Magnific (со слов владельца)

Промпт «подготовь фото к профессиональной печати… разрешение 4к…» + модель **Seedream 5 pro**,
расход ~1500 кредитов, на выходе JPEG в килобайты.

Это **не апскейлер**: Seedream — генеративная модель (`/api-reference/image-editing/seedream-4-5-edit/`,
`/api-reference/text-to-image/post-seedream-v4-5`). Следствия для печати:

- **сходство не гарантировано** — модель перерисовывает изображение, а не увеличивает его;
- **выход — сжатый JPEG фиксированного размера**, «4к» из промпта не контракт, а пожелание;
  килобайтный файл на 300 DPI непечатаем;
- **цена в 1500 кредитов** против €0.10–0.20 у профильного апскейлера.

Правильный инструмент под нашу задачу — `image-upscaler-precision` (сохраняет содержимое, текстуру и
структуру, детали не выдумывает). `image-upscaler-creative` — только для сравнения: он умеет дорисовывать,
для лиц реальных клиентов это риск. Цветокоррекция («фото тёмное») — отдельный шаг, дешевле делать
локально (OpenCV/PIL уже в зависимостях), а не платным генеративным проходом.

### Контракт Magnific (сверено с docs.magnific.com)

| | Creative | Precision V2 |
|---|---|---|
| POST | `/v1/ai/image-upscaler` | `/v1/ai/image-upscaler-precision-v2` |
| вход | base64 | base64 **или** публичный HTTPS-URL |
| масштаб | `2x/4x/8x/16x` | `2..16` |
| ручки | `optimized_for`, `prompt`, `creativity`/`hdr`/`resemblance`/`fractality` (−10..10), `engine` | `flavor` (`sublime/photo/photo_denoiser`), `sharpen`, `smart_grain`, `ultra_detail` |

Общее: заголовок `x-magnific-api-key`; ответ `{data:{task_id,status,generated[]}}`;
статусы `CREATED|IN_PROGRESS|COMPLETED|FAILED`; результат — poll `GET {endpoint}/{task_id}` либо `webhook_url`.
Лимиты: выход ≤ 25.3 Мпикс, 50 запросов/мин на ключ. Ключи Freepik работают на обоих хостах.

**Вебхуки:** заголовки `webhook-id`, `webhook-timestamp`, `webhook-signature`;
подпись = base64(HMAC-SHA256(secret, `webhook-id.webhook-timestamp.body`)), формат значения `v1,<sig>`.
Для локального теста не нужны (нет публичного URL) — используем polling.

**Цена (docs, Precision):** 640×480→2x ≈ €0.10, 640×480→4x ≈ €0.20, 1920×1080→2x ≈ €0.20 —
считается по площади выхода. В кредитах не опубликована → меряем фактическое списание в тесте.

### Риски

1. **Приватность** — фото клиентов уходят наружу. В [../задача.md](../задача.md) внешний API признан
   нежелательным для прода («максимум для быстрой проверки»); для теста берём не клиентский портрет.
2. **Размер выхода** — file-platform принимает ≤20 МБ, наш кап `ENHANCE_MAX_OUTPUT_PX=7200`.
   Magnific на 8x/16x это перебьёт → downscale + JPEG обязательны на нашей стороне.
3. **Таймаут** — book-editor ждёт результат максимум 180с (`ENHANCE_MAX_WAIT_MS`), HTTP-таймаут 30с
   на вызов. Если Magnific стабильно дольше — C3 придётся переводить на webhook/async.
4. **Egress с прода** — на codex OUTPUT для uid 109 закрыт по портам, весь исходящий в OpenVPN.
   Доступность `api.magnific.com` с бокса проверяется отдельно; локальный успех ничего не доказывает.

## План

- **L0 (эта ветка):** `scripts/magnific_smoke.py` — один вызов, замер времени/веса/разрешения и
  фактического списания кредитов. Сравнить precision vs creative на одном фото, свериться с тем,
  что даёт Seedream в вебе.
- **L1:** если качество/цена устраивают — второй провайдер в `enhance-service`
  (`ENHANCE_PROVIDER=local|magnific`), контракт C1 не меняется, book-editor и file-platform не трогаем.
- **L2:** включение `ENHANCE_ENABLED=true` + проверка egress с бокса.

## Результат

### Прогоны (2026-08-10)

| Движок | Вход | Выход | Время | Итог |
|---|---|---|---|---|
| precision-v2 | 1000×750 (уменьшенная копия) | 2000×1500, 4.95 МБ | 81с | ОК, но запрошен x4 — вернулся **x2** |
| precision (v1) | то же | — | 67с | `COMPLETED` с пустым `generated[]`, кредиты впустую |
| local_fix (PIL) | 4000×3000 оригинал | 3000×4000, 3.15 МБ | <1с | 0 кредитов |

Ключ рабочий, e2e через API проходит. Суммарный расход по кабинету — **180 кредитов**.
Кредиты в заголовках ответа не отдаются, только `X-RateLimit-*` (50/мин).

### Главный вывод: апскейлер решает не ту задачу

Реальное фото клиента (`reference-img1.jpeg`) — **пересъёмка бумажного отпечатка**: 12 Мп «пустых»
пикселей, EXIF-поворот, блик от вспышки, выцветший цвет, зерно фотобумаги, отсутствие деталей.
Апскейл здесь бесполезен: 12 Мп = 34×25 см при 300 DPI (печатать уже можно), а Precision по
определению не выдумывает детали — он увеличит зерно и блик. Плюс scale=2 от 12 Мп = 48 Мп,
что выше лимита 25.3 Мп: полноразмерный оригинал API вообще не примет.

Веб-результат владельца (Seedream 5 pro, ~1500 кредитов) действительно лучше: блик убран, цвет
восстановлен, детали резкие. Но это **перерисовка**, и у неё своя цена:
- выход **1328×1760 = 2.3 Мп**, то есть 11×15 см при 300 DPI — для разворота фотокниги мало,
  поверх всё равно нужен апскейл;
- кадр сменил пропорции 4:3 → 3:4 (края срезаны);
- лицо ребёнка реконструировано моделью — для детских фото в фотокниге сходство проверить нечем.

### Что бесплатно

`scripts/local_fix.py` (EXIF-ориентация + автоуровни + gray-world баланс белого + unsharp) за доли
секунды и 0 кредитов возвращает ориентацию, цвет и контраст — заметную часть разницы с вебом.
Не лечит: блик вспышки, зерно бумаги, отсутствующую детализацию.

**Следствие для пайплайна:** локальную коррекцию делать всегда и до платного вызова — иначе платим
за то, что чинится даром. Дальше по классу фото: «мало пикселей, кадр нормальный» → precision
(180 кредитов); «убитый скан» → генеративное восстановление (Seedream edit есть и в API) с
осознанным риском сходства, при необходимости + precision поверх.

### Открытые вопросы

1. `scale_factor: 4` вернул x2 — причина не выяснена (гипотеза: нормализация входа). Нужен
   контрольный прогон с `--scale 8`.
2. v1 `image-upscaler-precision` отдаёт пустой `generated[]` — формат ответа другой либо только webhook.
3. Кроп и поворот в вебе — сделала модель или владелец до загрузки? От этого зависит, годится ли
   генеративный путь для пакетной обработки.
4. Цена кредита в деньгах и стоимость Seedream-прохода на объёме (100 фото ≈ 150 000 кредитов).
