# AI-улучшение изображений в book-editor — направление

**Дата:** 2026-06-23
**Статус:** обсуждение (код не пишем)

## Задача

Перенести функционал AI-улучшения изображений (апскейл + восстановление лиц)
из черновика руководителя (`book-layout`, проект `1/от макса/.project`) в наш
сервис **book-editor** — добавить кнопку и функционал в окно просмотра изображений
(`PhotoPreviewModal.vue`).

## Источник (как сделано у Макса)

Три слоя:
1. **Python-микросервис `enhance-service`** (FastAPI, порт 8001): async-очередь с
   одним воркером. `POST /enhance/start` (file + опц. `target_w/target_h`) → `job_id`,
   `GET /enhance/status/{id}`, `GET /enhance/result/{id}`.
   Пайплайн: GFPGAN (лица, по умолч. off) → Real-ESRGAN ×2 (tile, CPU) → второй
   проход если масштаб >2.5× → ресайз под target → unsharp → JPEG q95.
   **Target-aware:** апскейл не вслепую ×2, а до точного числа пикселей под 300 DPI.
2. **NestJS-прокси**: адаптер `ImageEnhanceClient` с двумя реализациями
   (`AiEnhanceClient` → Python, `SharpEnhanceClient` → fallback) + фабрика по `/health`.
   `calculatePrintQuality()` считает effectiveDpi и requiredPixels по размеру
   разворота и доле ячейки.
3. **Nuxt UI**: кнопка «AI Улучшить» в модалке редактирования фото, прогресс-бар,
   переключатель «До/После», «Применить/Откатить». Оригинал не удаляется.

Грабли Макса (его `docs/knowledge/gotchas.md`): OOM на сервере без swap, нужен
swap 2GB, `ENABLE_GFPGAN=false` по умолчанию, пик RSS ~1.1ГБ, torchvision≥0.17 shim,
torch.load держит GIL → таймаут статуса 30с.

## Целевая архитектура (3 сервиса — отдельная ветка/review/merge в каждом)

1. **book-editor** — UI-кнопка в `PhotoPreviewModal.vue`, гейт по DPI, оркестрация,
   before/after.
2. **file-platform** — хранить улучшенную версию как **отдельный вариант** изображения
   (у сервиса уже есть `UploadImageVariant` + версионирование + статусы
   pending/processing/ready/failed + очередь/воркер; отдача `?variant=...`).
3. **Компьют** — enhance-микросервис Макса (self-host) ИЛИ внешний API.

## Решения

- **(3) Гейт по DPI** — СОГЛАСОВАНО: кнопку показывать только для фото с низким
  effectiveDpi (предв. порог `< 200`). Тот же расчёт даёт target-размер под 300 DPI.
- **(1) Провайдер компьюта** — ВЫБИРАЕМ (см. ниже). Паттерн адаптера сохраняем —
  provider swappable.
- **(2) Метрики сервера** — снимаем (см. ниже), чтобы решить self-host vs API.
- **(4) Где AI-вычисление + детали хранения варианта в file-platform** — ОТЛОЖЕНО,
  затрудняемся. Предв. рекомендация: компьют снаружи, file-platform только хранит/
  отдаёт вариант (сохраняет инвариант «не тащить AI/GPU в платформу»).

## Метрики сервера book-editor (хост `crm` / 85.92.110.56, Ubuntu 24.04)

Снято 2026-06-23 (`free -h`, `nproc`, `lscpu`, `df`, `nvidia-smi`, `docker ps`):
- **RAM 7.8 ГБ** (used 3.9 / free 2.1 / buff-cache 2.3 / **available 3.9**).
- **Swap 4 ГБ, занято 2 ГБ** (бокс свопит, но стабильно работает).
- **CPU: 4 vCPU @ 2 ГГц** (QEMU Virtual, медленные виртуальные ядра).
- **GPU: нет.** Диск: 43 ГБ свободно (под модели ~0.5 ГБ + temp — с запасом).
- `docker ps` пусто / нет docker → **file-platform на этом боксе не виден**
  (и в pm2 его нет) — где крутится, не подтверждено.
- Бокс общий: crm nest (`nestjs-app` 1.4ГБ), book-editor-backend (1.2ГБ),
  nuxt, auth, payment, vk, editor-assets-воркеры. nest/book-editor рестартуют 8–11 раз.

Сравнение с боксом Макса (1.9 ГБ RAM, ~1–2 ядра, 2 ГБ swap, no GPU), где enhance
уже работает: **у нас в 4× больше RAM и больше ядер** → по ёмкости проходит.

**Пересмотренный вердикт:** self-host на этом боксе для **low-volume MVP реалистичен**
(раньше переоценил риск OOM). Реальный риск — не ёмкость, а **контеншен**: ESRGAN-job
пинит CPU на 2–7 мин на медленных vCPU + скачок RAM на уже свопящем общем боксе.
Смягчение: один воркер, pm2 `max_memory_restart ~1.2ГБ`, `nice`/`cpulimit`,
DPI-гейт (режет объём). RAM хватает даже включить восстановление лиц (в отличие от Макса).
Перед деплоем — проверить качество бесплатно локально (Mac/Colab) на реальных фото.

## Метрики AI-бокса codex (2026-06-23) — РЕШЕНО: дом для MVP

`ssh codex` (`/opt/codex`, ai-assistant, порт 8090):
- **RAM 1.9 ГБ** (used 475М / free 450М / buff-cache 1.2Г / **available 1.5Г**).
- **Swap 2 ГБ, занято 1%** (не свопит, простаивает).
- **CPU 2 vCPU @ QEMU**, GPU нет. Диск 31 ГБ свободно.
- **load 0.0, pm2: только assistant-service 67МБ** — бокс почти пустой.

**Ключевое:** codex — тот же hardware-класс, что рабочий бокс Макса (1.9ГБ RAM + 2ГБ swap
+ 2 ядра + no GPU), но почти не нагружен. У Макса enhance крутится на таком же железе ещё
и под кабинетом. ⇒ **codex потянет enhance-service для low-volume MVP.**

**РЕШЕНИЕ по компьюту:** MVP — enhance-service на **codex** (не на crm). CRM не трогаем,
бесплатно, фото в своей инфре. Guardrails: `ENABLE_GFPGAN=false`, один воркер,
pm2 `max_memory_restart ~1.2ГБ`, `nice`/`cpulimit` (защитить ai-assistant на общих 2 ядрах).
Caveat: во время job ai-assistant может тормозить → следить за `AI_ASSISTANT_TIMEOUT_MS`.

**Этап 2 (генерация фотокниг):** codex слаб для генеративного ИИ (нужен GPU) → отдельный
GPU-бокс. Адаптер оставит book-editor/file-platform без изменений при переходе.

**Провайдер MVP фактически определён:** self-host open-source стек Макса
(Real-ESRGAN x2plus; CodeFormer/GFPGAN — опционально позже). Внешний API (Replicate) —
запасной для пиков, не основа (приватность).

## Стратегическое направление (уточнено 2026-06-23)

Руководитель задал рамку: **(1) CRM должна работать бесперебойно, (2) систему будем
масштабировать + больше функционала, (3) хотим, чтобы ИИ создавал фотокниги.**

Следствия:
- **Self-host на crm-боксе ОТПАДАЕТ** — тяжёлый CPU-компьют (ESRGAN 2–7 мин + спайк RAM
  на свопящем общем сервере) угрожает бесперебойности CRM.
- Нужен **отдельный масштабируемый AI-слой**, а не «прикрутить апскейл». Генерация
  фотокниг в перспективе = GPU-heavy.
- **Приватность**: личные фото клиентов → внешний API для прода нежелателен (макс. для
  быстрой проверки). Компьют держим в своей инфре.
- Связь book-editor ↔ AI — **async-очередь** (паттерн Макса) + адаптер `ImageEnhanceClient`
  (provider/железо меняем, не трогая book-editor и file-platform).

**Ключевой инсайт:** у нас уже есть AI-сервер — ai-assistant на `ssh codex` (`/opt/codex`,
порт 8090). Это естественный дом для enhance-service и будущей генерации фотокниг:
CRM не трогаем, бесплатно (бокс есть), фото в своей инфре, точка роста AI. Нужно снять
его метрики (потянет ли).

**Поэтапный путь:**
- Этап 0 (сейчас, бесплатно): проверить качество Real-ESRGAN+CodeFormer локально (Mac/Colab)
  на реальных фото.
- Этап 1 (MVP): enhance-service на AI-боксе (codex или отдельный дешёвый VPS, если codex слаб).
  Результат → file-platform вариант `enhanced`.
- Этап 2 (рост): AI-бокс CPU→GPU, на нём же генеративное «ИИ создаёт фотокниги».

## Скоуп

MVP = **только улучшение (апскейл) изображений**. Генерация фотокниг — отдельный
будущий этап (GPU-бокс), сейчас НЕ делаем.

## Лимиты и метрики (ОБЯЗАТЕЛЬНО — требование руководителя)

Причина: codex слабый (2 CPU, 2–7 мин/фото, single worker) + делит ядра с ai-assistant.
Массовые запросы без лимитов положат бокс. Защита — **оборона в глубину** по слоям.

**Защита от перегрузки:**
- **L0 UX (FE):** DPI-гейт (уже); кнопка disabled пока job in-flight; сообщения
  «очередь/лимит исчерпан».
- **L1 Политика (book-editor BE):** per-user квота (N/день); per-user concurrency = 1
  in-flight; глобальный дневной cap; **dedup** (не улучшать уже улучшенное/то же повторно).
- **L2 Глобальная очередь:** max длина → переполнение = `429/503` «сервис занят».
- **L3 Hard backstop (enhance на codex):** один воркер (есть у Макса) + bounded queue +
  cap входного размера/разрешения + job timeout 660с + TTL temp-файлов. Защищает бокс,
  даже если L0–L2 обойдут.

**Метрики/мониторинг:**
- enhance-service: расширить `/health` → `/metrics` (queue depth, jobs total/ok/err,
  avg/p95 time, активный job).
- book-editor BE: **персистить EnhanceJob в Postgres** (user, photoId, status, wait/proc
  time, in/out size, scale, error) — для квот + истории + дашборда (у Макса jobs в памяти,
  теряются при рестарте — наше улучшение).
- file-platform: статус/тайминг/размер варианта `enhanced` уже в БД — даром.
- Ресурсы: pm2 CPU/RAM/рестарты codex + **рестарты ai-assistant** (не топит ли сосед).
- Качество: applied vs reverted ratio.
- Алерты: очередь > порога, высокий error-rate, рестарты ai-assistant.

**Стартовые значения (tunable, откалибровать после бенчмарка Этапа 0):**
- 1 concurrent (hard), очередь ≤ ~10–20.
- per-user: 1 in-flight, ~20–50/день. Global: ~несколько сотен/день.
- вход ≤ ~24 Мпикс / ~20 МБ; job timeout 660с; TTL результата ~1ч.

## Этап 0 — результаты проверки качества (2026-06-23) — GO

Прогон Real-ESRGAN (ncnn-vulkan, модель `realesrgan-x4plus`) на 3 реальных low-DPI
портретах (480–640px) на Intel Mac (CPU, без GPU — прокси для codex).
Артефакты: `test-input/`, `test-output/`, `test-compare/` (bicubic слева vs AI справа),
инструмент в `tools/`.

**Качество — GO:**
- Чёткое стабильное улучшение vs bicubic: резче глаза/волосы/узоры/края.
- Лица достоверны — НЕТ галлюцинаций/смены черт (критично для книги про реальных людей).
  И это БЕЗ face-restoration (как у Макса по умолчанию).
- Улучшение реальное, но не «магия»: на мелких лицах выигрыш скромнее.

**Бенчмарк:** ~16–19 с/фото (480–640px → x4 ~2.5Мпикс) на CPU ncnn-vulkan.
Намного лучше 2–7 мин у Макса (у него Python/torch + крупные входы + double-pass + GFPGAN).
Low-DPI = маленький вход → быстро.

**x2 vs x4 (2026-06-23):** на портрете bicubic ≪ AI; **AI x2 ≈ AI x4 по качеству-на-пиксель**
(x2 даёт почти весь прирост над bicubic), но x4 = в 4× больше пикселей (выше предельный
DPI/размер печати) и в 4× больше файл (~8МБ vs ~2МБ). ⇒ подтверждает target-driven масштаб:
апскейлить ровно под размер ячейки (x2 хватает для обычных ячеек, x4 — для крупных/на разворот).
Артефакт: `test-compare/scales_compare.png`. (Внимание: ncnn `-s 2` с моделью x4plus даёт
БИТЫЙ тайловый результат — настоящий x2 = native x2plus или x4→downscale.)

**Находки для сборки:**
- **ncnn-vulkan легче/быстрее Python/torch** (~30МБ, без torch, мало RAM) → для codex
  предпочтительнее обернуть ncnn-бинарь в тонкий сервис, а не тащить torch-стек. Логику
  (очередь/лимиты/метрики) берём у Макса, движок — ncnn.
- Throughput выше ожидаемого → стартовые лимиты можно поднять (уточнить на реальном codex).
**Восстановление лиц (GFPGAN v1.4, weight=0.85) — проверено 2026-06-23:**
Артефакты: `test-output/*_gfpgan.png`, `test-compare/*_faces.png` (Real-ESRGAN слева vs GFPGAN справа).
- Плюс: чётче глаза/черты, особенно на МЕЛКИХ/мягких лицах (image2 — там выигрыш наибольший).
- Минус: **сглаживает кожу** (молодящий/«пластиковый» эффект), убирает морщины/текстуру →
  у пожилых лиц меняет характер; на очень мелких лицах риск «дорисовки».
- Скорость: дёшево, +6–7 с/фото на CPU (инференс на кропе 512×512).
- **Вывод:** делать **опцией (opt-in «улучшить лица»)**, а не всегда-вкл (как у Макса по умолч.).
  Рассмотреть **CodeFormer** (есть регулятор fidelity, часто натуральнее GFPGAN).
- RAM: GFPGAN модели ~520МБ пик; на codex (1.5ГБ свободно) с ESRGAN — тесно, но реально
  при последовательном запуске (как у Макса: GFPGAN → free → ESRGAN).

**Установка torch-стека — ВРАЖДЕБНА (важная находка):** basicsr + llvmlite/numba (нет LLVM,
сборка из исходников), build-isolation, numpy 1.x↔2.x конфликт torch↔scipy, torchvision≥0.17
убрал functional_tensor (shim), python-urllib SSL fail на скачивании моделей. Понадобились:
`--only-binary=llvmlite,numba`, пины `numpy==1.26.4 scipy==1.11.4 scikit-image==0.22`, shim,
SSL-обход, curl моделей. ⇒ В ПРОДЕ этот стек на слабом боксе хрупок — ещё довод за **ncnn**
(один бинарь, без torch) как движок; torch только для разовых экспериментов.

## Открытые вопросы

Закрыто: метрики crm+codex сняты; компьют = codex; провайдер = self-host Real-ESRGAN;
хранение = file-platform вариант `enhanced`; гейт = low-DPI; лимиты/метрики — дизайн заложен.

Осталось:
1. **Этап 0 не сделан**: проверить качество (Real-ESRGAN+CodeFormer на 3–5 реальных фото)
   + бенчмарк времени/RAM на codex-классе → откалибровать лимиты.
2. **Где физически крутится file-platform** — на crm в docker не видно, на codex pm2 только
   ai-assistant. Подтвердить перед детализацией хранения варианта `enhanced`.
3. **Детали варианта `enhanced` в file-platform**: enum закрытый (preview/xs/sm/md/lg) +
   варианты сейчас генерит внутренний воркер из clean. Нужен intake внешне-произведённого
   артефакта (компьют снаружи) — продумать, не нарушая инвариантов платформы.
4. **DPI-гейт**: по размещению (точный per-cell DPI) vs по разрешению фото (проще для MVP);
   точный порог (предв. `< 200`). В book-editor нет аналога `calculatePrintQuality` — портировать.
5. Финальные значения лимитов — после бенчмарка (п.1).
