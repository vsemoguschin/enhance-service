# Провайдеры движка: что стоит, почему и чего стоит ждать

Справочник по `ENHANCE_PROVIDER`. Контракт **C1** одинаков для всех — book-editor не знает,
кто считает картинку. Замеры и история выбора — в [audits/2026-08-10-magnific-api-test.md](audits/2026-08-10-magnific-api-test.md).

## Текущее состояние прода (2026-08-11)

`ENHANCE_PROVIDER=codex`, пресет `identity`, 3 воркера, таймаут 150 с,
запасной провайдер `magnific` (`ENHANCE_FALLBACK`).

## Сравнение

| | codex | magnific | local |
|---|---|---|---|
| движок | Codex CLI + встроенный imagegen | Seedream 4.5 edit / Precision | ncnn Real-ESRGAN |
| время на фото | ~130 с (полный цикл C1) | ~25 с | минуты без GPU |
| оплата | подписка, ~23 тыс. токенов за прогон | ~50 кредитов ≈ 4.6 ₽ | своё железо |
| качество | лучшее из проверенных: не пересобирает кадр | хорошее на обычных форматах | слабее |
| выход | ~1.6 Мп (рост ×1.8) | 3.7–4.2 Мп | до кэпа |
| пропускная способность | ~150 фото/час (3 воркера) | ~480 фото/час (4 воркера) | непригодно |

**Почему codex основной:** на групповом кадре Seedream дорисовал двух несуществующих людей,
nano-banana дорисовала головной убор — codex сохранил и состав, и композицию, и пропорцию.
Владелец принял размен «медленнее, зато без выдумок и без кредитов».

## Ограничители, которые упрутся раньше ресурсов

- **Magnific:** 50 запросов/мин на ключ, причём опрос статуса тратит тот же лимит. При 4 воркерах
  и опросе раз в 8 с выходит ~38 запросов/мин. Сервис считает эту оценку на старте и предупреждает.
- **Codex:** лимиты подписки OpenAI (неизвестны, проявятся при 8+ параллельных). По ресурсам бокса
  запас большой: три параллельных прогона заняли 97 с, ~115 МБ на всех и load 0.49 из 2.0.
- **book-editor:** ждёт результат `ENHANCE_MAX_WAIT_MS` (прод 300 с). Очередь не должна разрастаться
  настолько, чтобы клиент упирался в это раньше сервера.

## Гейт на генерацию (только magnific)

Seedream выбирает пропорцию выхода из фиксированного списка и на нестандартном формате
**пересобирает композицию**, а не дополняет края. Поэтому `_generative_is_safe()` отдаёт
апскейлеру кадры с пропорцией > 2.0 или < 0.5 и те, что расходятся с пресетами более чем
на `MAGNIFIC_MAX_ASPECT_DRIFT` (0.20). Промптом это не лечится — проверено.

Инвариант для любого провайдера: **пропорция кадра не меняется**. Enhanced подставляется вместо
оригинала, и поехавший аспект сломал бы кроп в редакторе. У magnific это обеспечивают
pad зеркальными полями до пресета и обратный crop.

## Промпты

Тексты — в [app/prompts.py](../app/prompts.py), общие для сервиса и `scripts/magnific_smoke.py`.

- `identity` (дефолт) — структура подсмотрена у Codex CLI: поля вместо абзаца, явный
  `identity-preserve`, длинный список `Avoid`. На селфи перестал перерисовывать фон.
- `texture` — против «пластика», прямые запреты на бьюти-ретушь.
- `old-photo` — сканы старых отпечатков, не осовременивает колорит.
- `restore`, `detail`, `web` — осторожный, максимально детальный и сравнительный.

Главный вывод: **запреты работают лучше просьб**, но ни один промпт не удерживает модель от
перерисовки лица — дрейф зависит от размера лица в пикселях.

## Поведение при сбоях (с 2026-08-12)

На задачу действует **один сквозной срок**, а не сумма таймаутов отдельных вызовов: codex — до
`CODEX_TIMEOUT_S` (150с), magnific — до `MAGNIFIC_TIMEOUT_S` (150с) с потолками 90/30/90с на
отправку, опрос и скачивание. При недоступной сети задача падает по сроку, а не висит: замер —
недоступный хост при сроке 6с отваливается за 6с (прежняя схема дала бы ~360с).

Зависший агент снимается вместе с группой процессов (`killpg`), иначе потомки `codex` держали
pipe и воркер оставался «занят» без единого процесса.

Худший случай на задачу: 150с codex + 150с magnific ≈ 300с — совпадает с ожиданием book-editor,
то есть пользователь получает ошибку примерно тогда же, когда сдаётся сервис.

## Эксплуатация

- Провайдер и его готовность видно в `/health`: `provider`, `engine` (для codex — найден ли CLI,
  для magnific — задан ли ключ, значение не печатается).
- Нагрузка и воркеры — в `/metrics` (`workers`, `active`, `queue_len`).
- codex требует рабочего sandbox: на Ubuntu 24.04 нужен AppArmor-профиль для bubblewrap,
  см. [operations.md](operations.md). Без него агент отвечает `FAIL`, не сумев прочитать файл.
- Переключение и откат — одна переменная плюс рестарт, см. [deploy-runbook.md](deploy-runbook.md).
